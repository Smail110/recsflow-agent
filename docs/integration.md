# Передача команде Recsflow

Код работает независимо от Recsflow. Контракт реальной платформы отсутствует; URL, токены, методы аутентификации и формат ответов не предполагались.

## Замена источника

Реализуйте протокол `RecommendationProvider`, преобразуя ответы реальной платформы в `Item`. Для отсутствующих атрибутов не подставляйте фиктивные значения. Если нельзя заполнить обязательные `kind`, `genre`, `tone`, `minutes`, сначала согласуйте схему: поддержите `unknown/null` в модели, фильтрах и объяснениях. Пустое значение должно означать отсутствие данных, а не совпадение с ограничением.

```python
from recagent.agent import Agent
from recagent.api import create_app
from company.recsflow_adapter import RecsflowAdapter  # будущая реализация вашей команды

provider = RecsflowAdapter(...)  # согласованные URL, auth, таймауты
app = create_app(Agent(provider=provider, mode="ollama"))
```

Это иллюстрация точки внедрения зависимости, а не уже существующий `company`-пакет. Встроенный `DemoProvider` — рабочий пример всех четырёх методов.

`retrieve` должен учитывать фильтры до усечения списка, либо обеспечивать достаточно широкий пул и пагинацию. Агент повторно проверяет строгие ограничения после `lookup`. `history` в данном прототипе интерпретируется как список уже знакомых/потреблённых объектов: они исключаются из выдачи, а их жанры используются для мягкого ранжирования. Если реальная история включает простые показы, клики, покупки, дизлайки, нужны отдельные типизированные события; не передавайте все события как потребление.

Поле `quality` — служебная оценка реранкера 0..1. В демо она сгенерирована. В адаптере используйте нормализованный реальный score или пересмотрите сигнатуру `retrieve`, чтобы передавать исходные score отдельно. В `Item.synthetic` для реальных объектов устанавливайте `False`.

## Что запросить у заказчика

- OpenAPI/пример запросов retrieval и metadata lookup, тестовый доступ и таймауты.
- Каталог со стабильными ID, правилами обновления, обязательными/неизвестными полями и семантикой длительности.
- Схему пользовательских событий, разрешённые способы использования истории и ID текущего пользователя от слоя авторизации.
- Ограничения доступности контента, локали, возраста и лицензии, если применимы.
- Целевые SLO, RPS, бюджет вычислений, модель/оборудование и критерий успешного диалога.

Ни один из этих пунктов не нужен для локального запуска демо.

## Что изменить перед production

API должен получать проверенный user_id от middleware, а feedback проверять владельца сессии. Сейчас session_id — непредсказуемый UUID, но самостоятельной системы авторизации нет. Вынести сессии в Redis/БД, обеспечить блокировку/версионирование между worker, TTL и лимит запросов на пользователя, добавить circuit breaker и метрики ошибок интеграции. Не включать трассировку во внешние системы без согласованной политики данных.

Формальный endpoint может сохранить `POST /v1/chat`: ответ уже включает нормализованный запрос, рекомендации, evidence и наблюдаемость. Уберите внутреннюю диагностику из публичного ответа, если она не предназначена клиентам. Чат можно подключить к REST, заменив прямой вызов `Agent.chat` на HTTP; текущий Streamlit намеренно запускается одним процессом без обязательного второго сервиса.
