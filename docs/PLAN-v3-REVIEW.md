Дата проверки: 14.09.2026. Основание: текущие файлы проекта, `PLAN-v3.md`, `EVAL-PLAN.md` и предоставленная страница «Задача №8». Это предложение по корректировке, а не изменение статуса исходного плана. Незакоммиченные изменения в оракуле, сценариях, тестах и pyproject учитывались как текущее рабочее состояние.

## Вывод

Направление v3 правильное: независимая оценка, сравнение политик уточнений, честная имитация закрытой платформы и воспроизводимая поставка. Но календарь перегружен инфраструктурой, а часть описания исходного состояния устарела. Главная работа сейчас — соединить уже написанные компоненты в измеряемый сквозной сценарий и проверить требования задания. Redis, Grafana, LoRA и обучаемый реранкер не должны задерживать это.

## Исправления самого плана

1. **Убрать обещание гарантированной интеграции.** Предлагаемый контракт и одинаковые тесты снижают риск несовместимости, но не доказывают, что неизвестная платформа будет ему соответствовать. Зафиксировать: это требования адаптера и reference mock; фактическое отображение API проверяется при появлении доступа. Утверждение, что заказчик реализует платформу именно под этот контракт, требует отдельного подтверждения.
2. **Добавить разрешение названия в item_id.** `Agent` вызывает `find_title`, а в OpenAPI нет соответствующей операции. Выбрать поиск метаданных по названию либо локальный индекс из выгрузки. Определить неоднозначное название, опечатку, отсутствие совпадения. Проверить «похожее на» и навигацию через HTTP-адаптер.
3. **Развести отказ объяснений и невозможность проверить ограничения.** Если метаданные доступны, можно выдать проверенные объекты без объяснения. Если доступен только сырой список платформы, нельзя утверждать, что соблюдены «не мрачный» или «один сезон». Такой fallback должен явно сообщать об отсутствии проверки; в eval он не считается удовлетворением ограничений. При недоступности retrieval — отдельный исход unavailable, а не обычный no_results.
4. **Перенести адаптивные вопросы раньше масштабирования.** Это прямое требование задания. Redis с optimistic concurrency и несколько воркеров не заменяют доказательства, что вопрос помогает пользователю.
5. **Сделать LLM-симулятор и LLM-судью явными результатами фазы оценки.** Они указаны в задании. В новом runner код хранит theta и смысл ответа, LLM формулирует реплику; судья — дополнительный сигнал. Считать завершённые вызовы, ошибки и fallback отдельно. Сохранить примеры диалогов и расхождений с оракулом.
6. **Актуализировать список дефектов.** Размер 84 и `rng.uniform(.55,.98)` уже не описывают текущий генератор. Эвристический реранкер остаётся, но изменение распределения quality само по себе не доказывает улучшение ранжирования.
7. **Не называть success=1 тавтологией только из-за совпадения проверяемых полей.** В старом evaluator expected задан отдельно от Query: это полезная проверка соблюдения явных ограничений. Её недостаток — маленький узкий набор и отсутствие оценки скрытых предпочтений/пользы диалога. Новый оракул решает другую, более широкую задачу.
8. **Разделить требования задания и улучшения проекта.** LoRA, шесть классификаторов интентов, Redis, Grafana, полный OTel и multi-stage Docker не перечислены как обязательные артефакты. Настраиваемые тон и длина объяснений, LLM-оценка, бюджет вызовов, скринкаст и воспроизводимость — перечислены. Последние должны иметь собственные проверки готовности.

## Минимальный убедительный эксперимент

- B0: случайная выдача и popularity как отдельные простые контроли. Проверять ожидаемые различия на наборе; не требовать провала каждого случайного ответа и не подгонять оракул, чтобы popularity обязательно проиграл.
- B1: имитация платформы без диалога. Текущий `DemoProvider.retrieve` уже принимает Query и фильтрует: нельзя незаметно дать такому baseline извлечённые ограничения и назвать его «user_id → список». Описать его отдельное поведение.
- B2: зафиксированная текущая версия агента.
- Fixed и Adaptive: одинаковые parser, provider, ranking, лимиты ходов и модели; меняется только политика вопросов. Не менять ранжирование одновременно с вопросами.
- Oracle ceiling: диагностический потолок, а не доступная агенту конфигурация. Нормированное улучшение не вычислять при нулевом или слишком малом знаменателе.

До сравнения определить основной success: приемлемость всех показанных объектов, наличие хотя бы одного подходящего либо иной критерий. Не выбирать определение после просмотра результатов. Дополнительно показывать hard-constraint violations, hit-rate@k, размер выдачи, utility, число вопросов, отказы пользователя, задержки, LLM-вызовы и токены. Защититься от улучшения success простой выдачей одного объекта вместо пяти.

Политика спрашивает, если оценка ожидаемого выигрыша от ответа превышает стоимость дополнительного хода. Information gain по слотам может быть приближением, но уменьшение неопределённости ещё не доказывает улучшение выдачи. Агент не имеет доступа к theta, acceptable_ids или функции судьи. Нужны остановка по бюджету/терпению и обработка «не знаю / без разницы».

Для сравнения политик нужен симулятор, отвечающий на фактически заданный вопрос из theta. Фиксированная последовательность реплик полезна для регрессий, но не заменяет такую симуляцию. Одинаковые исходные профили и seeds используются для парных сравнений.

Holdout отделять по профилям и, для проверки языкового обобщения, по семействам формулировок; другой seed сам по себе не гарантирует новых языковых конструкций. Bootstrap делать по независимым единицам: по профилю, если один профиль порождает несколько диалогов. Не обещать различимость 5–8 п.п. только на основании 200 сценариев: она зависит от данных и парных расхождений. Зафиксировать метрику, пороги и конфигурацию до финального holdout. Отсутствие значимого выигрыша — допустимый исследовательский результат.

Исправить отдельный существующий дефект: `scripts/evaluate.py` передаёт пустую историю в `validate_evidence`; проверка утверждений о персонализации должна получать реальную историю данного сценария. Добавить негативный пример с подменённым источником evidence и проверить текст объяснения, а не только корректность ссылок.

## Что отложить первым

1. LoRA и сравнение шести моделей интентов: оставить rules/локальную LLM и разбор ошибок по четырём интентам задания.
2. Обучаемый реранкер: сначала стабильная объяснимая эвристика и изолированное сравнение вопросов.
3. Redis, multi-worker и распределённые блокировки: план продуктивизации; внедрять до сдачи только при необходимости выбранной нагрузки.
4. Grafana/Prometheus и полное трассирование: сначала структурированные логи и времена стадий.
5. Расширение набора внешних датасетов: использовать имеющуюся калибровку, документировать происхождение. Не превращать сбор данных в самостоятельный проект.

Сохраняются простые таймауты, бюджет вызовов, ограничение сессий, понятные ошибки и проверки grounding. Не следует откладывать всё управление отказами вместе с тяжёлой инфраструктурой.

## Организационные сведения, которые действительно влияют на план

- Сколько участников и времени есть до дедлайна: в задании указан состав 3–4 человека. Для индивидуальной работы объём дополнительных экспериментов особенно важно сократить.
- Есть ли уточнения заказчика из встречи: что он принимает вместо реального подключения, основной домен демонстрации и ожидаемое поведение уточнений. Пока отсутствие доступа трактуется по PLAN-v3, а не как независимо подтверждённый факт.
- На каком компьютере проверяющий сможет запустить LLM и какой путь воспроизведения предложен без неё.
- Кто проверит вручную выборку реплик и запишет скринкаст.

Старые блокеры из раздела 7 v3 следует перепроверить, а не переносить автоматически. Для продолжения анализа и написания кода уже имеющихся данных достаточно. Согласование новых установок — вопрос среды, не отдельный продуктовый этап.
