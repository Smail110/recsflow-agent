# Воспроизводимая проверка диалогового контракта

`product-contract-ru-v1` — внутренний ID набора для проверки наряду с DEV.
Это 12 диалогов / 20 ходов,
написанных AI для проверки операций, а не реальные пользовательские данные и не
финальный независимый тест. Набор зафиксирован до первого запуска на нём;
автор знал прежние классы ошибок. Метки не извлекаются из Query или ответов агента.

Проверяются четыре intent, исправление длительности, накопление и снятие исключений,
снятие лимита, смена домена, «ещё», неизвестный уровень и необязательное уточнение.
Размер выбран по покрытию этих операций, без заявления статистической мощности.
Ходы одного диалога зависимы. Общие шаблоны языка и домена также ограничивают выводы.

## Сборка данных

После установки зависимостей проекта, из корня workspace:

```powershell
python -m scripts.build_product_contract --output artifacts/contract-rebuild-a.json
python -m scripts.build_product_contract --output artifacts/contract-rebuild-b.json
Get-FileHash -Algorithm SHA256 artifacts/contract-rebuild-a.json
Get-FileHash -Algorithm SHA256 artifacts/contract-rebuild-b.json
```

Оба файла должны иметь SHA-256
`c18bc46c5d8a3275f3763b5a9fcdc55d162253e7e78b9095b6b2833311581958`.
Seed 137 фиксирует синтетический каталог; реплики и независимые накопительные
spoken-метки заданы в генераторе. `.manifest.json` фиксирует версии, количество
диалогов/ходов, seed и хеш генератора. Это проверка целостности, не цифровая подпись.
Повторяемость байтов подтверждена тестами и отдельным review.

## Запуск baseline и workflow

```powershell
python -m scripts.evaluate_product_contract --cohort artifacts/contract-rebuild-a.json --manifest artifacts/contract-rebuild-a.manifest.json --mode rules --implementation baseline-v1 --output artifacts/contract-run/rules.json
python -m scripts.evaluate_product_contract --cohort artifacts/contract-rebuild-a.json --manifest artifacts/contract-rebuild-a.manifest.json --mode ollama --implementation workflow-v2 --compare artifacts/contract-run/rules.json --output artifacts/contract-run/workflow.json
```

Для второй команды нужна Ollama с закреплённой `qwen3:8b`; digest проверяется до
inference и после него. Используйте новые output-пути: runner не перезаписывает
существующие измерения. Перед запуском он сохраняет protocol, фактическую factory
конфигурацию, transport options, хеши каталога и исходников. Агент получает
публичный каталог и пользовательские реплики; метки остаются только у оценщика.
Неполный прогон сохраняется с `complete=false` и не получает успешную оценку.

Это сравнение двух систем: меняются и реализация, и способ разбора. Оно не доказывает
причинность одной переменной. Фиксированный seed и temperature не гарантируют
побайтового совпадения нового LLM-ответа на другом оборудовании. **Данные** при
сборке совпадают побайтово; сохранённые ответы можно оценить без inference.

## Значение метрик

`observable_delivery` требует допустимого состояния, наличия/отсутствия выдачи,
известных уникальных ID и соблюдения размеченных spoken-условий. Учитываются
точные/запрещённые ID и неповторение предыдущих объектов в сценарии «ещё».
Каждый ход каждого диалога остаётся в знаменателе; успешен только полностью
успешный диалог. Хеш фактического каталога проверяется, включая сравнение систем.

`active_query_diagnostics` показывает расхождения внутреннего состояния отдельно.
Он не создаёт ground truth и не превращает допустимую выдачу в измерение полноты
поиска. Проверка `similar` подтверждает явные ограничения и исключение seed, но
не человеческую оценку сходства. Clear/include дополнительно требуют component
invariants: по одной допустимой выдаче нельзя доказать, что лишнее ограничение снято.
Template grounding — ограниченная проверка распознаваемых утверждений, не полная
проверка естественного языка. Скрытая удовлетворённость здесь не вычисляется.

DEV и CONTRACT имеют разные критерии. Их результаты нужно читать отдельно:
смена критерия не означает улучшение агента. Текущие измерения и определения
приведены в [описании оценки](../EVALUATION.md).

## Настоящие диалоги

Отдельно подготовлен пилот ReDial: закреплённый официальный
источник, хеши, 24 английских prefix, 48 разных workers, две одинаковые сборки.
Это материал для разметки; человеческий gold, русский перевод и соответствие
каталогу не выдумываются. До их проверки метрики качества на ReDial не считаются.
Его роль относительно текущей оценки описана в
[DATA-PROVENANCE.md](../DATA-PROVENANCE.md).

## Проверки реализации

```powershell
python -m pytest -q tests/unit/test_observable_product.py tests/unit/test_product_contract_data.py tests/unit/test_redial_pilot.py
```

Эти команды не требуют закрытых наборов. Они проверяют воспроизводимость
сценариев и работу оценщика, а не качество ответов живых пользователей.
