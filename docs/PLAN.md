Статус: на согласовании. Baseline-коммит `fc8699e` — точка отсчёта, всё до неё сохранено.

## 0. С нуля или поверх существующего?

Рекомендация: **не с нуля**, а структурная переработка. Причины:

- Из 7 «ожидаемых артефактов» задачи 5 уже закрыты кодом: слой инструментов
  (retrieval / metadata lookup / фильтры / реранкер / уточняющий вопрос), оркестратор
  на LangGraph с памятью сессии и бюджетом вызовов, grounding с проверкой каждого
  утверждения, REST-эндпоинт, демо-чат.
- 16 тестов проходят (`pytest -q`, 6.0 s). Переписывание с нуля сжигает 3-4 дня
  и создаёт риск регрессий на ровном месте.
- Baseline-коммит позволяет в любой момент сделать diff и откатиться.

Что **заменяется полностью**: генератор каталога, слой провайдеров, ранжирование,
политика вопросов, harness оценки, датасет интентов.
Что **сохраняется**: `grounding.py`, скелет `agent.py` (граф), `api.py`, протокол
провайдера, тестовый каркас.

Если решение всё же «с нуля» — структура этапов ниже не меняется, добавляется только
этап чистой заготовки каталогов/пакетов.

## 1. Что оценивает задача (целевая функция всего плана)

Явные метрики из формулировки:

| Метрика задачи | Где измеряем |
|---|---|
| success rate | harness диалогов |
| среднее число уточнений | harness диалогов |
| доля галлюцинаций в объяснениях | программная сверка evidence (первично) + LLM-судья (совещательно) |
| латентность | HTTP-нагрузка, оба режима |
| стоимость LLM-вызовов | модель стоимости на токенах |
| анализ узких мест, план продуктивизации | отчёт, раздел 6 |

Pass/fail-артефакты сдачи: рабочий репозиторий + README + зависимости, отчёт PDF/HTML,
Dockerfile и запуск, скринкаст 2-5 мин, воспроизводимость ключевых результатов,
unit-тесты, notebook, конфиги.

Принцип: **ни одной цифры, не полученной реальным прогоном.** Синтетика маркируется
как синтетика. Это не «для красоты» — раздел «Данные» задачи прямо требует
воспроизводимый скрипт генерации с фиксированным seed, а завышенные метрики
на протёкшем датасете обнуляют доверие ко всему отчёту.

## 2. Ключевые дефекты текущего состояния (что именно чиним)

1. `success_rate = 1.0` тавтологичен: oracle в `scripts/evaluate.py` проверяет те же
   поля, что агент применяет как hard-фильтры в `providers.py:matches()`. Непустая
   выдача проходит по построению; к качеству ранжирования метрика слепа.
2. Ранжирование фактически случайное: `item.quality + affinity + similarity`,
   где `quality = rng.uniform(.55, .98)`.
3. Датасет интентов протёк: 160 строк, **29 уникальных текстов**, 9 шаблонов;
   `train_test_split` кладёт идентичные строки в train и test.
4. Нагрузочный тест в `rules`-режиме: `agent_llm_calls: 0`, LLM под нагрузкой не мерился.
5. `monetary_cost: null` при явном требовании стоимости.
6. Интеграции с Recsflow нет вообще, хотя задача формулирует роль агента как
   «использует Recsflow как набор инструментов».
7. Политика уточнений не соответствует требованию «спрашивает слот, только если это
   ожидаемо повышает качество выдачи» — сейчас спрашивает по отсутствию формата/темы.
8. Каталог 84 объекта — на таком объёме фильтры, пустая выдача и лимит 100 кандидатов
   не показательны.
9. Формальные артефакты: нет коммитов/remote (коммит сделан, remote нет), нет скринкаста,
   Docker не собирался, README содержит machine-specific утверждение
   «На текущем компьютере окружение уже установлено».
10. Мелкий баг оценки: `validate_evidence(..., history=[])` — любое evidence с
    `relation="history"` засчитывается как неподтверждённое. На историях даст ложный
    рост `unsupported_claim_rate`.

## 3. Целевая архитектура

```
recagent/
  models.py            Pydantic-контракты (Query, Item, Evidence, Recommendation, ...)
  catalog/
    generator.py       воспроизводимый синтетический каталог + профили пользователей
    users.py           скрытые предпочтения theta (только для оракула/симулятора)
  providers/
    base.py            Protocol RecommendationProvider
    memory.py          in-process провайдер (тесты, быстрая оценка)
    recsflow.py        HTTP-адаптер к контракту Recsflow + retry + circuit breaker
    mock_platform.py   mock-платформа Recsflow (FastAPI), третий сервис в compose
  parsing.py           правила + Ollama structured output
  intents/             классификатор намерений: rules / ollama / sklearn / LoRA
  questions.py         адаптивная политика вопросов (information gain)
  ranking.py           фьюжн источников + обучаемый реранкер + diversity
  grounding.py         сверка evidence, шаблоны объяснений, тон/длина под бренд
  session.py           хранилище сессий (память; интерфейс под Redis)
  agent.py             граф LangGraph + деградация к выдаче Recsflow
  api.py               FastAPI REST
scripts/
  prepare_data.py  prepare_hf_dataset.py  train_lora.py  evaluate_dialogues.py
  evaluate_parsing.py  load_test.py  cost_model.py  build_report.py  make_deck.py
tests/  docs/  report/  notebooks/  deploy/
```

Поток одного хода:
`запрос -> извлечение слотов -> валидация -> (уточнение | retrieval Recsflow)
-> metadata -> hard filters -> fusion -> rerank -> diversity -> grounding -> ответ`

## 4. Этапы работ

### WP1. Данные: каталог и пользователи

- Генератор каталога ~3000 объектов (seed=42, параметр `--size`): film/series/course,
  ~12 жанров, tone, seasons 1-8, episodes, minutes, level, practical, year, quality,
  popularity. Атрибуты должны допускать непустую и пустую выдачу на типовых запросах.
- Профили пользователей: скрытый вектор предпочтений theta (веса по жанру/тону,
  допуск по длительности, level, practical) + типизированная история событий
  (`viewed` / `liked` / `disliked`), а не плоский список «потреблённого».
- Cold-start профиль (без истории) и профиль с богатой историей.
- `null` в атрибутах = «нет данных», а не «совпало с ограничением» — явно в модели
  и фильтрах (это же требование уже записано в `docs/integration.md`, теперь соблюдаем).

Done when: `python -m recagent.catalog --seed 42` детерминирован; два запуска дают
идентичный SHA-256; тесты на распределения атрибутов проходят.

### WP2. Harness оценки (делаем измерение раньше оптимизации)

- **Слой A — парсинг.** Датасет `utterance -> expected Query`. Метрика: field-level
  accuracy/precision/recall по каждому слоту, отдельно отрицания и противоречия.
  Независимо от LLM, детерминированно.
- **Слой B — диалоги.** Симулятор: LLM (`qwen3:8b`) делает только поверхностную
  реализацию реплик; **скрытые предпочтения и правдивость ответов задаются кодом**.
  Так получаем реализм от LLM и детерминированный оракул от кода.
  Success = агент вернул хотя бы один объект из приемлемого множества
  (`utility(item, theta) >= порог`) в пределах бюджета ходов.
  Метрики: success rate, ходов до успеха, среднее число уточнений, доля «пустых»
  уточнений (вопрос не изменил top-k), доля пустых выдач, обнаружение противоречий,
  fallback rate, латентность, LLM-вызовы, токены.
- **Слой C — объяснения.** Первично программная сверка evidence по каталогу;
  LLM-судья совещательно, его вердикт не является критерием приёмки (как сейчас).
- Набор сценариев: 12 -> **150-300 диалогов**, 15 типов (неполный запрос, несколько
  ограничений, смена формата, «покажи ещё», дизлайк, неизвестный объект, пустая выдача,
  противоречие, снятие ограничения, «не знаю/неважно», повторная рекомендация,
  похожий объект, новый пользователь, богатая история, adversarial/prompt-injection).
- **Dev/holdout разделение по seed**: dev seed=42, holdout seed=1337, holdout не
  используется при подборе промптов и порогов. В отчёте обе цифры.
- Bootstrap-доверительные интервалы по диалогам; сравнение конфигураций на одних
  и тех же диалогах (paired).
- Починить баг №10 (передавать реальную history в `validate_evidence`).

Done when: есть честный baseline — ожидаемо заметно ниже 1.0, и это нормально.
Цифра baseline фиксируется в отчёте как точка отсчёта.

### WP3. Recsflow: mock-платформа и адаптер

- Контракт берём из формулировки задачи: «на вход — айди пользователя, на выход —
  список айди айтемов» + metadata lookup. Оформляем как предложение контракта,
  а не как реконструкцию недоступного API (так же честно, как сейчас).
- `mock_platform.py` — отдельный FastAPI-сервис: `POST /v1/recommendations`,
  `GET /v1/items/{id}`, `GET /v1/users/{id}/history`, искусственные задержки,
  инжектируемые сбои (`?fail_rate=`) для проверки деградации.
- `RecsflowProvider` на httpx: таймауты, повторные попытки, circuit breaker,
  кэш метаданных.
- **Деградация к классической выдаче Recsflow при сбоях** — названное требование задачи.
  Сейчас при падении провайдера агент возвращает ошибку; должно вернуть сырой список
  платформы с пометкой «объяснения недоступны».
- Hard-фильтры применяются после `lookup` (уже есть) + телеметрия recall до/после
  фильтров — это закрывает пункт 5 «Границ прототипа».
- Третий сервис в `compose.yaml`, профиль `with-platform`.

Done when: интеграционный тест гоняет диалог через HTTP mock; при `fail_rate=1.0`
пользователь получает список без объяснений, а не 500; тесты деградации зелёные.

### WP4. Ранжирование и адаптивные вопросы (ядро вклада)

- Fusion: score платформы + популярность + аффинити истории + сходство с seed.
  Нормировка и веса — в конфиге YAML, не в коде.
- Обучаемый реранкер: логистическая регрессия / градиентный бустинг (scikit-learn)
  на синтетическом фидбеке от симулятора. Сравнение «эвристика vs обученный» —
  полноценный ablation. Нейросетевой реранкер не делаем: не на чем обучать.
- Diversity: MMR-lite по жанру/тону, ограничение повторов, учёт показанного.
- **Adaptive question policy** — главный содержательный вклад:
  ```
  gain(slot) = H(top-k | now) - SUM_v P(v) * H(top-k | answer=v)
               - lambda * effort(slot) - mu * latency(slot)
  ```
  вопросы только при `gain > порог`, максимум 2-3 подряд, один слот за вопрос,
  не спрашивать известное, поддержка «не знаю/неважно», при лимите — лучшая доступная
  выдача, при пустой выдаче — вопрос «какое ограничение ослабить».
  Варианты ответа формируются из фактических значений каталога, а не из воздуха.
- Ablation: fixed questions vs adaptive questions vs no questions на одних диалогах.

Done when: adaptive questions снижают среднее число уточнений без падения success
rate (или повышают success rate при том же числе уточнений) на dev-наборе,
результат подтверждён на holdout, CI не пересекают ноль либо честно об этом сказано.

### WP5. Интенты и LoRA

- Новый генератор датасета: 1200+ **уникальных** реплик, комбинаторика шаблонов,
  дедупликация по нормализованному тексту, метка семейства шаблона.
- **Group split по семейству шаблона** — ни одно семейство не пересекает границу
  train/val/test. Это и есть устранение дефекта №3.
- Сравнение четырёх подходов: правила / Ollama zero-shot / rubert-tiny2 full
  fine-tune / rubert-tiny2 + LoRA (PEFT). Метрики: accuracy, macro-F1, F1 по классам,
  матрица ошибок, slot F1, латентность, размер адаптера.
- Зависимости тяжёлые (torch ~2 ГБ). Сначала ставим и меряем время обучения на
  одной эпохе; если не влезает в бюджет дней — LoRA остаётся воспроизводимым
  скриптом с `--dry-run` и заранее прогнанным результатом, а основной упор делается
  на sklearn-классификатор. Решение принимаем по замеру, а не по обещанию.
- Формулировка в отчёте: данные синтетические, обучено на синтетике, продуктовых
  данных заказчика не было. Никаких заявлений об обучении на реальных диалогах.

Done when: метрики LoRA получены на group-split, утечки нет (проверяется тестом на
пересечение семейств), сравнение четырёх подходов сведено в одну таблицу.

### WP6. Нагрузка и стоимость

- Нагрузочный тест **в обоих режимах**: rules (быстрый путь) и ollama (реальные
  LLM-вызовы). p50/p95/p99, RPS, ошибки, токены, число вызовов.
- Keep-alive против нового соединения на запрос — сейчас 400 мс p50 это в основном
  overhead открытия соединения; меряем оба варианта и явно это объясняем.
- Модель стоимости вместо `null`: токены x публичная цена hosted-аналога = «эквивалент
  стоимости», плюс отдельная оценка локального GPU-часа. Обе цифры маркируются как
  оценка, формула и источник цены — в отчёте.
- Проверка бюджета LLM-вызовов на сессию под нагрузкой.

Done when: `report/load-test-*.json` содержит оба режима и непустой `monetary_cost`
с задокументированной формулой.

  В MovieLens нет атрибутов tone / seasons / level / practical — то есть ровно тех

- Заявления об обучении на реальных данных заказчика.
