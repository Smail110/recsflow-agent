## 0. Новое входное условие: доступа к Recsflow НЕ будет

Заказчик отказал в доступе к Recsflow, песочнице и контракту API и планирует
внедрять интеграцию самостоятельно позже.

### Что это меняет

1. **Контракт интеграции становится первоклассным артефактом сдачи**, а не приложением.
   Заказчик будет реализовывать платформу под НАШ контракт. Значит контракт должен быть
   полным, машиночитаемым и проверенным тестами.
2. **Mock-платформа перестаёт быть игрушкой** — она становится reference-реализацией
   контракта. Пишем её spec-driven: из OpenAPI, с проверкой соответствия схемы.
   Когда заказчик реализует настоящий Recsflow, **те же contract-тесты должны пройти
   без изменений**. Это и есть гарантия бесшовного внедрения.
3. **Ценность смещается с «мы подключились» на «мы передаём готовый к внедрению пакет»**:
   контракт + адаптер + пример адаптера + contract-тесты + runbook + чек-лист интеграции.
   Раздел задачи «план продуктивизации» получает буквальное наполнение.
4. **Уходят риски ожидания.** Больше не зависим от заказчика — полная автономия до дедлайна.
5. **Честные ограничения в отчёт:** recall фильтров измерен на синтетическом каталоге,
   а не на реальной платформе; деградация проверена на mock, а не на проде;
   авторизация и user_id не предоставляются, описан требуемый middleware.

### Что НЕ меняется
Продукт — диалоговый слой. Метрики задачи — success rate, число уточнений,
доля галлюцинаций, латентность, стоимость. Продавые практики из v2 остаются.

## 1. Ключевое решение по методологии: бейзлайн первым

Прибор должен уметь говорить «плохо». Текущая `success_rate = 1.0` тавтологична:
оракул проверяет те же поля, что агент применяет как hard-фильтры.

Четыре точки отсчёта (детали в `EVAL-PLAN.md`):
- **B0** random/popularity — sanity floor, обязан провалиться (тест самого прибора)
- **B1** сырой список Recsflow без диалога — бизнес-обоснование «зачем RecAgent»
- **B2** текущая система — техническая точка отсчёта
- **B3** oracle ceiling (знает theta) — нормировка `(ours-B2)/(B3-B2)`

Лестница вмешательств L1..L6, каждая добавляет ровно одно. Ключевое сравнение —
**L4 (fixed questions) vs L5 (adaptive questions)**: прямое доказательство требования
задачи «спрашивает слот, только если это ожидаемо повышает качество выдачи».

Статистика: paired-сравнение на одних диалогах, bootstrap CI (1000 ресемплов, 95%),
заявление об улучшении только если интервал не пересекает ноль.
Dev seed=42 / holdout seed=1337, holdout не участвует в подборе порогов.
Пороги фиксируются коммитом ДО прогона.

## 3. Контракт интеграции — содержание

`docs/contract/openapi.yaml` + JSON Schemas + `docs/contract/INTEGRATION-CHECKLIST.md`.

Эндпоинты, которые нам нужны от платформы:
```
POST /v1/recommendations   {user_id, limit, filters?}     -> {items:[{item_id, score}], model_version, generated_at}
GET  /v1/items/{item_id}                                  -> метаданные
POST /v1/items:batchGet    {item_ids:[...]}               -> метаданные пачкой (важно для латентности)
GET  /v1/users/{user_id}/history?types=&limit=            -> типизированные события
GET  /health                                              -> liveness
GET  /ready                                               -> readiness
```

Обязательные требования к контракту:
- семантика `score`: диапазон, нормирован ли, сравним ли между запросами
- `null` в атрибутах = «нет данных», а не «совпало с ограничением»
- типизированные события (`viewed`/`liked`/`disliked`), а не плоский список
- пагинация/курсор и поведение при `limit` больше доступного пула
- коды ошибок и формат (предлагаем RFC 7807), таймауты, идемпотентность
- версионирование, `X-Request-ID` сквозной корреляции
- стабильность item_id между вызовами (нужно для кэша и evidence)

Что отдаём заказчику в пакете внедрения:
1. `openapi.yaml` + JSON Schemas
2. `RecsflowProvider` — готовый async-адаптер (httpx, tenacity retry, circuit breaker, таймауты)
3. `mock_platform.py` — reference-реализация контракта, запускается из compose
4. `tests/contract/` — прогоняются и против mock, и против их реальной платформы
5. `INTEGRATION-CHECKLIST.md` — шаги, что предоставить, как проверить
6. `runbook.md` — диагностика по трейсу, уровни деградации, бюджеты
7. ADR — обоснования решений (почему монолит, почему не k8s, почему sklearn-реранкер)

## 6. Дефекты текущего кода, которые чиним

1. `success_rate = 1.0` тавтологичен -> независимый оракул по theta (P2)
2. Ранжирование фактически случайное (`quality = rng.uniform(.55,.98)`) -> fusion + reranker (P5)
3. Датасет интентов протёк (160 строк / 29 уникальных) -> group split по семейству (P7)
4. Нагрузочный тест без LLM (`agent_llm_calls: 0`) -> оба режима (P6)
5. `monetary_cost: null` -> cost accountant (P6)
6. Нет интеграции с Recsflow -> контракт + mock + адаптер (P1/P3)
7. Политика уточнений не по приросту качества -> information gain (P5)
8. Каталог 84 объекта -> ~3000 (P2)
9. README machine-specific, Docker не собирался, нет скринкаста -> P8
10. Баг `validate_evidence(..., history=[])` -> передавать реальную историю (P2)
11. Синхронный I/O блокирует воркер -> async (P3/P4)
12. In-process сессии, «запускать одним worker» -> Redis (P4)
13. При падении провайдера ошибка вместо деградации -> лестница уровней (P3)

## 8. Честные ограничения для отчёта

1. Доступа к Recsflow не было. Контракт — наше предложение; заказчик реализует
   интеграцию самостоятельно. Mock-платформа — reference-реализация этого контракта.
2. Каталог, профили пользователей и диалоги сгенерированы; распределения откалиброваны
   по открытым наборам (IMDb non-commercial, MovieLens, Kinopoisk MIT, ReDial CC-BY-4.0).
3. Метрики характеризуют диалоговый слой, а не качество рекомендаций платформы.
4. LLM-симулятор и LLM-судья могут иметь коррелированные смещения; судья совещателен,
   критерий приёмки — независимый оракул.
5. Исправления делались по dev-набору; holdout не участвовал в подборе, обе цифры в отчёте.
6. Локальная стоимость оценивается по явным допущениям (hosted-эквивалент + GPU-час),
   а не измеряется по электроэнергии.
7. Деградация и recall фильтров проверены на mock и синтетическом каталоге.
