# Как измеряется исходное качество

Этот этап соединяет генератор D3 с агентом и независимым оракулом. Он отвечает на вопрос «где текущая система ошибается» и создаёт точку отсчёта для следующих изменений.

## Запуск

Из корня установленного проекта, в активированном Python-окружении:

```bash
python -m scripts.evaluate_baselines --check
```

На Windows без активации окружения:

```powershell
.\.venv\Scripts\python.exe -m scripts.evaluate_baselines --check
```

По умолчанию выполняются 200 dev-сценариев в режиме rules. Интернет и запущенная LLM не нужны. Полный отчёт сохраняется в `report/baselines-local.json`, который исключён из Git. `--size 30 --resamples 100` подходит для быстрой диагностики; полный прогон использует 1000 bootstrap-выборок.

`--mode ollama` включает локальную LLM только для текущего агента. Это последовательный эксперимент, не нагрузочный тест. `--split holdout` предназначен для финальной оценки после фиксации параметров; CI выполняет только dev. Старый `scripts.evaluate` остаётся коротким набором регрессионных сценариев и отдельным экспериментом с LLM-судьёй.

## С чем сравниваем

| Имя в отчёте | Доступная информация | Поведение |
|---|---|---|
| random | Каталог | Пять случайных объектов; seed привязан к сценарию |
| popularity | Каталог и popularity | Пять самых популярных объектов |
| platform_quality | user_id, каталог | DemoProvider с пустым Query, без диалога; сортировка по quality |
| current | Только реплики пользователя и каталог | Настоящий Agent, отдельная сессия на сценарий |
| oracle | Скрытые предпочтения и ground truth | Правильный исход и лучшие приемлемые объекты |

`platform_quality` — имитация списка платформы, а не качество настоящего Recsflow. Все измерения пока в режиме нового пользователя без истории. Эксперимент с персонализацией будет отдельным изменением.

Оракул и критерии строятся до запуска всех конфигураций. Агент получает только ChatRequest: user_id, session_id, message. Его Query и фильтры не используются для определения приемлемых объектов.

## Как читать метрики

- `final_success_rate`: финальный исход совпал с ожидаемым, все показанные объекты приемлемы, бюджет уточнений соблюдён, выдача заполнена до min(5, число приемлемых объектов). Именно эта метрика используется в парных сравнениях.
- `success_rate`: дополнительно проверены промежуточные состояния агента, соблюдение ограничений на каждом ходе, отсутствие повторов в сценарии «ещё» и валидность evidence. У списочных контролей нет промежуточных ходов, поэтому сравнивать с ними пользу диалога следует по final_success_rate.
- `failure_counts` и `by_kind`: причины ошибок и разрез по типу сценария. Сумма причин может превышать число неуспешных сценариев.
- `hard_constraint_violations`: число показанных объектов с нарушением озвученных ограничений, по всем ходам агента; у списочных контролей — только по финальной выдаче.
- `mean_slate_size`: средний размер финальной выдачи. Защищает от улучшения процента успеха простой выдачей меньшего числа объектов.
- `invalid_evidence_rate`: доля evidence, отвергнутых продуктовым валидатором. Без evidence значение null. Это не независимая оценка текста и не измерение галлюцинаций свободной LLM-генерации.

Парные интервалы показывают разницу final_success текущего агента и каждого базового метода. Bootstrap пересэмплирует целые профили, сохраняя связанные диалоги вместе. Отрицательный или пересекающий ноль интервал не подтверждает улучшение.

Отчёт содержит Git commit и dirty-флаг, хеш Python-исходников, хеш каталога и сценариев, seeds, режим и команду запуска. Сценарии генерируются воспроизводимо; их многомегабайтные JSONL не нужны в репозитории. При необходимости выгрузить их: `python -m evals.scenarios`.

Для компактного результата в репозитории добавьте `--summary-output report/baseline-dev.json`. Он содержит те же метрики и сведения о запуске, но без полных записей диалогов.

## Что проверяет CI

После тестов выполняется полный dev-прогон с `--check`. Проверки требуют принятия оракульного потолка и не более 10% успехов случайной выдачи на сценариях рекомендаций. Это проверки измерителя, а не обещание высокого качества агента. Полный JSON доступен в артефакте `dev-baselines` соответствующего запуска GitHub Actions.

## Ограничения этапа

Реплики воспроизводятся по фиксированному сценарию ровно один раз. Дополнительный ответ на финальный уточняющий вопрос не подставляется, даже если генератор хранит такой ответ. Поэтому этот прогон не оценивает пользу адаптивной политики; для неё нужен отдельный интерактивный симулятор. Финальный clarify вместо ожидаемой выдачи честно считается неуспехом.

Dev и holdout разделены по профилям, но пока используют общие семейства языковых шаблонов. Это не доказательство обобщения на новые формулировки. Латентность измеряется локально последовательно, без HTTP-конкуренции; стоимость и качество LLM нельзя выводить из rules-прогона.
