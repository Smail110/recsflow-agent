# Проверка поставки

Перед сдачей я проверяю установку из отдельной копии и соответствие отчёта
опубликованным результатам. Ниже — состав поставки и порядок проверки.

## Состав

Основные документы:

- `README.md` — задача, возможности, запуск, результаты и карта проекта.
- `docs/PROJECT-BRIEF.md` — требования задания.
- `docs/SUBMISSION-STATUS.md` — выполненные пункты и ограничения.
- `docs/ARCHITECTURE.md` — компоненты и поток запроса.
- `docs/EVALUATION.md` — метрики, даты, данные и границы выводов.
- `docs/DATA-PROVENANCE.md` — происхождение данных.
- `docs/REPRODUCE.md` и `docs/runbook.md` — установка и работа сервисов.
- `docs/CLIENT-ONBOARDING.md` — подключение второго mock-клиента.
- `docs/contract/INTEGRATION-CHECKLIST.md` — входы для настоящей интеграции.
- `docs/data/PRODUCT-CONTRACT.md` — сборка открытого CONTRACT-набора.
- `docs/DEVELOPMENT-ROADMAP.md` — план развития с критериями приёмки.
- `docs/RELEASE-CHECKLIST.md` — проверка состава и воспроизводимости.
- `report/REPORT.md` — авторский отчёт о решении, опытах и следующих шагах.
- `data/README.md` — назначение синтетических входов и команды генерации.

К документам прилагаются исходники, конфигурации, зависимости и lockfile,
тесты, notebook, Dockerfile, Compose, генераторы и синтетические входы оценки.
Внешние датасеты передаются ссылками в документации. Для сгенерированных
данных сохраняются скрипт, параметры и seed.
Отчёт — `report/index.html`; его источники — `report/evidence/` и
`report/selection.json`. Видео — `report/demo.mp4` с описанием записи
`report/video.json`.

## Сборка локального дерева

Из рабочей копии:

```powershell
python -m scripts.prepare_git_snapshot --output dist/git-candidate-YYYYMMDD
```

Папка назначения должна быть новой. Команда копирует текущие файлы по
явному списку, проверяет SHA-256 выбранных доказательств и локальные ссылки,
записывает `PUBLIC-MANIFEST.json`. Она не создаёт коммит и не выполняет push.
Перед созданием коммита нужно просмотреть получившийся список файлов.

## Приёмка

1. Сверить allowlist, список файлов и manifest. Исключить `.env`, ключи,
   виртуальные окружения, кэши, runtime-логи, временные файлы, веса моделей,
   сырые внешние данные и закрытые наборы. Отдельно проверить Git-историю,
   если передаётся репозиторий: отсутствие файла в последнем дереве не
   исключает его из предыдущих коммитов.
2. Создать отдельную чистую копию выбранного дерева. Установить зависимости
   по lockfile, выполнить `pip check`, тесты, Ruff и проверку контракта.
   Команды приведены в [REPRODUCE.md](REPRODUCE.md). Закрытые исследовательские
   suites не требуются для демо и не запускаются при его приёмке.
3. Выполнить notebook в rules и Ollama, проверить отдельные HTTP-процессы.
   Убедиться, что используется исходный код чистой копии, а не установленный
   пакет из рабочего каталога.
4. Запустить Docker Compose: config, build, up, ps, health/readiness и чат.
   Для параллельной проверки использовать отдельные project name и порты.
   В ответе должны быть подходящие карточки, `mode=ollama` и отсутствие
   неожиданного fallback. Отдельно проверяется управляемый отказ LLM.
5. Сверить README, таблицы оценки и HTML с исходными JSON. Для каждого числа
   должны быть известны дата, входы и критерий. Старые измерения нагрузки и
   LLM-ролей нельзя выдавать за повторный прогон окончательного кода.
6. Просмотреть видео полностью: 2–5 минут, реальный интерфейс, читаемые
   ответы и паузы, плавная прокрутка. Дата и способ записи должны быть
   указаны. Смонтированная демонстрация не подменяет замер latency.
7. Открыть ссылки из README и публичных документов в чистой копии. Пути
   к локальным невыбранным артефактам не считаются доступными источниками.
8. Сохранить внешнюю запись приёмки: состав, SHA-256 архива, команды,
   окружение и результаты. Не помещать хеш архива внутрь самого архива.

Перед публикацией окончательные изменения проходят `git diff --check` и
независимый review. Если после проверки меняются runtime-файлы, необходимо
повторить связанные тесты и smoke. Для локального прототипа настоящие
Recsflow endpoint и credentials не нужны; для внешней интеграции обязательны.
