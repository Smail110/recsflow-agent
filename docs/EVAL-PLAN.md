# Методология оценки: бейзлайн, лестница сравнений, статистический протокол

Принцип: **сначала измерительный прибор, потом улучшения.** Никакой фичи без
зафиксированного бейзлайна, к которому её можно сравнить.

## 1. Почему бейзлайн первым

Текущая цифра `success_rate = 1.0` получена потому, что оракул в `scripts/evaluate.py`
проверяет те же поля, которые агент применяет как hard-фильтры в `providers.py:matches()`.
Система и критерий написаны друг под друга. Любая непустая выдача проходит по построению.

Это называется **измерительный прибор без нуля и без шкалы**. Он не может ошибиться,
значит он ничего не измеряет.

Следствие: первая работа — не новая фича, а прибор, который **способен сказать «плохо»**.

## 2. Четыре точки отсчёта (все обязательны)

### B0 — Sanity floor: «случайная выдача»
Случайный или популярностный список, тот же формат ответа.
**Должен быть хуже всех остальных.** Если B0 не хуже — harness сломан, всё остальное
бессмысленно. Это тест самого прибора, а не системы. Отдельно проверяем, что
приемлемое множество theta не покрывает весь каталог (иначе любой ответ «успешен»).

### B1 — Product baseline: «платформа без диалога»
Сырой список Recsflow по истории пользователя: без разбора запроса, без уточнений,
без объяснений, без фильтров по запросу.
Отвечает на вопрос **«зачем вообще нужен RecAgent»** — это бизнес-обоснование проекта.
Разрыв B1 -> B2..B6 и есть ценность диалогового слоя в цифрах.

### B2 — Technical baseline: текущая система
`rules`-режим, текущее ранжирование (`quality + affinity + similarity`),
текущая политика уточнений, текущие шаблоны объяснений.
Это честная точка отсчёта для каждого улучшения. Ожидается, что на новом оракуле
она даст заметно меньше 1.0 — и это правильный результат, а не провал.

### B3 — Oracle ceiling: «читер»
Знает скрытый вектор theta и выбирает оптимальные объекты. Не сдаётся как решение,
нужен для нормировки:
```
normalized_improvement = (ours - B2) / (B3 - B2)
```
Показывает, какую долю достижимого улучшения мы закрыли. Гораздо сильнее на защите,
чем голая цифра «success rate 0.71», потому что контекстуализирует её.

## 3. Лестница вмешательств (каждая ступень добавляет ровно одно)

| # | Конфигурация | Что проверяет |
|---|---|---|
| B0 | random / popularity | sanity floor |
| B1 | сырой Recsflow | ценность диалога как такового |
| B2 | rules + hard filters + текущий sort | технический бейзлайн |
| L1 | + fusion нескольких источников | польза многоступенчатого retrieval |
| L2 | + обучаемый реранкер (sklearn) | польза обучения против эвристики |
| L3 | + diversity (MMR) | разнообразие против чистой релевантности |
| L4 | + fixed questions | польза уточнений вообще |
| L5 | + adaptive questions (information gain) | **главный вклад**: польза адаптивности |
| L6 | + LLM-разбор (ollama) против rules | польза LLM в парсинге |

Ключевые сравнения для защиты:
- **L4 vs L5** — прямое доказательство требования задачи «спрашивает слот, только если
  это ожидаемо повышает качество выдачи». Если L5 не лучше L4 — честно пишем об этом.
- **B2 vs L5** — суммарный эффект.
- **L5 vs L6** — где LLM действительно нужна, а где достаточно правил.

Ablation в обратную сторону (выключаем по одному из полной конфигурации) — вторая
таблица того же эксперимента, даёт проверку симметрии выводов.

## 4. Отдельный слой: парсинг (свой бейзлайн, своя таблица)

Диалоговые метрики не изолируют качество извлечения слотов. Поэтому отдельный золотой
набор `utterance -> expected Query`, ~400-600 реплик: комбинаторная генерация +
ручная верификация + adversarial-случаи (составные отрицания, противоречия, инъекции).

| # | Метод | Метрики |
|---|---|---|
| A0 | всегда пустой Query | null-бейзлайн |
| A1 | правила (текущие regex) | field-level P/R/F1 по каждому слоту |
| A2 | Ollama zero-shot | accuracy, macro-F1, slot F1, латентность |
| A3 | sklearn TF-IDF + logreg | + стоимость инференса |
| A4 | rubert-tiny2 full fine-tune | |
| A5 | rubert-tiny2 + LoRA | + размер адаптера |

Отдельно: точность на отрицаниях и на противоречиях — там, где текущий код уже
ошибался (в отчёте зафиксирован баг «не слишком мрачный»).

## 5. Статистический протокол

- **Paired-сравнение:** все конфигурации на одном наборе диалогов, одинаковые theta,
  одинаковые seed, одинаковая реализация реплик. Разница по парам снижает дисперсию
  в разы по сравнению с независимыми прогонами.
- **Bootstrap CI:** 1000 ресемплов по диалогам, 95% интервал.
- **Критерий заявления об улучшении:** доверительный интервал разницы не пересекает ноль.
  Иначе пишем «различие статистически не подтверждено», а не «улучшилось на 3%».
- **Порядок мощности:** при n=200 диалогов и paired-дизайне различимы эффекты порядка
  5-8 п.п. для success rate. При текущих 12 сценариях не различимо практически ничего —
  поэтому расширение набора не косметика, а условие осмысленности выводов.
- **Dev / holdout:** dev seed=42, holdout seed=1337. Holdout не участвует в подборе
  промптов, порогов gain и весов fusion. В отчёте обе цифры, расхождение объясняется.

## 6. Заморозка бейзлайна и gate в CI

После первого честного прогона фиксируем:
```
evals/baseline.json     <- в git, изменять только осознанным коммитом
evals/thresholds.yaml   <- success_rate >= X, hallucination_rate <= Y, p95 <= Z
.github/workflows/evals.yml
```
CI прогоняет dev-набор и падает при регрессии против `baseline.json`.
Это превращает метрики из строчки в отчёте в **регрессионные тесты** — ровно та
практика, которой LLM-команды защищаются от тихой деградации после смены промпта
или версии модели. Одновременно это закрывает требование воспроизводимости:
она становится машинно проверяемой, а не описанной словами.

## 7. Порядок работ (исправляет календарь v2 в части P2)

1. theta-профили пользователей + генератор каталога.
2. Оракул со скрытой полезностью + приемлемое множество.
3. Симулятор (LLM делает поверхностную реализацию реплик; правдивость задаёт код).
4. Прогон B0 — прибор должен показать «хуже всех». Если нет — правим оракул/пороги.
5. Прогон B1, B2, B3 — получаем четыре цифры.
6. **Фиксируем `baseline.json`, коммит.**
7. Только теперь строим L1..L6, каждое сразу с paired-сравнением.

Антипаттерн, которого избегаем: сначала написать adaptive questions, потом искать
бейзлайн. Именно так появляются цифры, которые не воспроизводятся и не защищаются.
